# 汎用Webアプリ開発テンプレート：アプリ内部構成・コード設計

更新日: 2026-10-31  
状態: 6項目の基本方針確定（実装・検証は別途）

## 1. 目的・関連設計

React + TypeScript、Node.js + TypeScriptを使う、特定の業務アプリに依存しないテンプレートのコード構成と責務を定める。Projectを使う業務などをハードコードしない。

- [認証・認可・BFF設計](azure-webapp-bff-auth-security-and-authorization-cache.md)
- [REST API共通仕様](rest-api-common-standards.md)
- [Tenant・User・Resourceスコープ管理](tenant-user-resource-scope-management.md)
- [Azure構成・環境設計](azure-webapp-resource-and-environment-design.md)

本書は既存設計の認証方式、API契約、スコープ制御、Azure配置を再定義しない。認証設計の未検証事項は別途PoCを行う。旧標準資料に残るSWA + MSALの記載を、本書の現行BFF構成に混在させない。

## 2. 決定事項

| # | 設計項目 | 確定方針 |
|---|---|---|
| 1 | リポジトリ・アプリの分割 | A：業務アプリごとに1リポジトリ。フロント・BFF・APIを別パッケージとして管理 |
| 2 | アプリ内部のフォルダ構成 | A：機能単位にまとめ、機能内で役割を分離 |
| 3 | フロント・BFF・APIの責務 | A：表示はフロント、ブラウザ対応はBFF、業務処理・認可・DBアクセスはAPI |
| 4 | 業務処理とDBアクセスの分離 | A：ルート → Service → Repositoryの3役を基本とする |
| 5 | 共通コード・型・入力スキーマ | A：API契約を共有し、サーバー専用コードは別パッケージに分離 |
| 6 | 設定管理・例外処理 | A：設定は起動時に検証・集約。例外は各アプリの共通ハンドラーでHTTP応答へ変換 |

点数は会話上の比較評価であり、仕様・品質保証値ではない。本書には確定方針を記載する。

## 3. リポジトリ構成

```text
apps/
  web/                     React SPA
  bff/                     ブラウザ向けBFF
  api/                     業務API
packages/
  contracts/               API入出力型・Zodスキーマ
  server-common/           サーバー専用の共通処理
```

- 各アプリを別パッケージ・ビルド単位にし、1つの変更としてレビュー可能にする。
- フロントのビルド成果物はBFFと一緒にApp Service①から配信する。業務APIはApp Service②へ別途デプロイする。
- packages配下は実際に共有するコードができた段階で作成する。空の共通層を先行して増やさない。
- パッケージマネージャー、ワークスペース機構、ビルドツール、Webフレームワークの具体製品は本書では未決定。

## 4. 機能単位の配置

関連コードを features/{機能名}/ にまとめ、機能の中で役割を分離する。共通処理は機能の外に置く。

APIの構成例：

```text
apps/api/src/
  features/
    sample/
      sample.routes.ts
      sample.service.ts
      sample.repository.ts
  config/
  shared/
    errors/
    http/
```

- 上記は配置例。全機能に不要なファイルや層を機械的に作らない。
- フロントも機能単位を基本とし、画面・コンポーネント・データ取得処理等をまとめる。
- BFFは認証連携・API呼出し等の責務に合わせて構成し、業務APIのServiceやRepositoryを重複実装しない。
- 厳格なDomain/UseCase等の多層構成や、分離のためだけのクラス・インターフェースを標準必須にしない。

## 5. レイヤーの責務

| 配置先 | 担当 |
|---|---|
| フロント | 画面表示、入力操作、表示用入力チェック、画面状態 |
| BFF | 認証済みセッションの確認、CSRF対策、API向けトークン取得・付与、API呼出し |
| API | JWT検証、業務認可、正式な入力検証、業務ルール、DBアクセス |

### フロント

表示用の入力検証や権限に応じたUI制御は可能。ただしAPI側の入力検証・認可を省略する根拠にはしない。DBアクセスやサーバー専用コードをブラウザへ持ち込まない。

### BFF

画面向けのレスポンス整形、複数APIの結果集約は許可する。業務ルール・業務認可・業務DBアクセスはAPIへ集約し、API直接呼出しでも同じルールを適用する。

Easy Authとトークン取得の詳細は認証設計に従う。Principalから独自JWTへの変換・再署名を行う構成にはしない。

### API内の3役

| 役割 | 担当 |
|---|---|
| ルート | HTTP入出力、入力スキーマ検証、Service呼出し、成功レスポンスの生成 |
| Service | 業務ルール、対象に対する認可判断、業務処理の組立て |
| Repository | DB操作、Tenant/Project等のスコープを限定した問い合わせ・更新 |

JWT検証や共通認可チェックはAPIの共通処理として適用可能だが、対象Resourceの実所属・操作条件も確認する。Repositoryには既存スコープ設計の制約を適用し、読取・更新・削除等で越境アクセスを防ぐ。BFF経由と直接API呼出しに同等の認可を適用する。

ServiceにSQLやHTTPレスポンス生成を混在させず、Repositoryに画面制御を持ち込まない。トランザクション境界・接続管理の詳細はDB設計で決める。

## 6. 共有パッケージと依存関係

### packages/contracts

APIの入出力型とZodスキーマを共有する。ブラウザでも利用できる範囲に限定し、DBエンティティ、認証トークン、秘密情報、サーバー用設定・ドライバーに依存させない。TypeScriptの型共有だけで実行時検証済みとは扱わない。

### packages/server-common

BFFとAPIなどで実際に共有するサーバー専用処理を配置する。webからの参照は禁止する。業務固有ロジック・SQLは各APIの機能フォルダに残し、単に重複して見えるという理由で共通化しない。

### 依存の原則

- web → contracts
- bff → contracts、必要時server-common
- api → contracts、必要時server-common
- contractsはappsやserver-commonに依存させない。
- apps同士のソース直接参照で業務APIを迂回しない。BFFからAPIへは定めたHTTP契約で呼び出す。

公開入口やパッケージ設定等でブラウザ側へのサーバーコード混入を防ぐ。OpenAPIと共有スキーマの整合・生成方法はAPI詳細設計で決定する。

## 7. 設定管理

各アプリの config/ に設定の読込みと検証を集約する。環境変数の必須項目・形式を起動時に検証し、不備があれば必要な処理を開始せず、原因を安全に記録する。

- 機能ごとに環境変数を直接読む実装を散在させない。
- Azure側の通常設定、MI、必要時のKey Vaultは既存環境設計に従う。
- 検証エラーで秘密の値をログへ出力しない。
- フロントに渡す設定は公開可能な値のみ。フロントのビルドに含めた設定は利用者から閲覧可能として扱う。
- 各アプリの設定を集約する方針であり、外部の独自設定サービスを標準必須にするものではない。

## 8. 例外処理

API・BFFそれぞれに共通エラーハンドラーを置く。業務処理で発生したエラーを、既存API仕様のRFC 9457 Problem Detailsと整合するHTTP応答に変換する。

- Service等は「対象なし」「更新競合」等の意味を持つエラーを伝え、共通ハンドラーが404・409等へ変換する。これらは説明例で、全エラーコード体系の確定ではない。
- 共通の業務エラー定義は shared/errors/、HTTPへの変換は shared/http/ 等へ配置する。
- 内部スタックトレース、SQL、Cookie、トークン、秘密情報を応答へ含めない。調査用ログは機密情報を除外し、既存の相関ID・監査方針に従う。
- 回復処理・後始末・適切な意味のエラーへの変換が必要な場所だけ個別に捕捉する。各ルートで同じtry/catchと応答生成を繰り返さない。
- 外部の共通エラー処理サービスは標準必須にしない。監視への送信と、HTTPエラー変換は別の責務とする。
- タイムアウト、リトライ、二重登録防止、依存先障害時の詳細動作は別途共通設計する。

## 9. 実装時の確認事項

- フロントがサーバー専用コード・設定に依存していない。
- 業務ルールをBFFに重複配置せず、直接API呼出しにも適用できる。
- ルート・Service・Repositoryの責務とスコープ制御を確認する。
- API側で入力検証・認可を実施し、UIや共有型だけを信用しない。
- 設定不備を起動時に検知し、応答・ログに機密情報を出さない。
- 共通エラーハンドラーとProblem Detailsの整合を確認する。

本書はコード設計の決定事項であり、スターターコードやCI/CDの実装・テスト完了を意味しない。
