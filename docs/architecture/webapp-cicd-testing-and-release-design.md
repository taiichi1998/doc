# 汎用Webアプリ開発テンプレート：CI/CD・テスト・リリース設計

更新日: 2026-11-02  
状態: 基本方針確定・詳細案を含む初版（暫定項目と保留事項は明記）

## 1. 目的・関連設計

特定の業務アプリに依存せず、個人開発からチーム開発まで利用できるCI/CD・テスト・リリースの方針を定める。本書は設計書であり、Azure DevOpsへの設定・パイプライン実装・動作検証の完了を意味しない。

- [Azure構成・環境設計](azure-webapp-resource-and-environment-design.md)
- [アプリ内部構成・コード設計](webapp-application-code-structure-design.md)
- [DB設計・変更管理](webapp-database-design-and-change-management.md)
- [認証・認可・BFF設計](azure-webapp-bff-auth-security-and-authorization-cache.md)
- [スコープ管理](tenant-user-resource-scope-management.md)
- [REST API共通仕様](rest-api-common-standards.md)

Azureリソースの配置・ネットワーク・バックアップは既存設計に従う。DBスキーマの正本はSQL Projectとし、DACPAC・データ移行の手順はDB設計を参照する。

## 2. 確定事項

| 項目 | 方針 |
|---|---|
| 開発基盤 | Azure DevOps（Boards・Repos・Pipelines）を標準採用 |
| 作業管理 | Agileプロセス。個人開発にも適用可能 |
| ブランチ方式 | GitHub Flow：mainと短命な作業ブランチ、PRを基本とする |
| PRの人承認 | 作成者以外の承認を一律必須にしない。チーム要件に応じて追加可能 |
| AIレビュー | 別途構築済みの自作AIレビュアーを任意適用 |
| dev反映 | mainマージ後、CI成功で自動反映 |
| 本番反映 | 検証済み成果物を手動承認後に反映 |
| 成果物 | 環境間で同じ成果物を昇格。本番向けにビルドし直さない |
| 実行環境 | Self-hostedを基本とする。本番用実行環境・Agent Pool・権限を分離 |
| リリース単位 | フロント＋BFF・API・DBの対応する版を1つのリリースとして管理 |
| DB反映 | DB変更がある場合のみ実施。影響の大きい変更等は追加承認 |
| テスト方針 | PRで高速検査・重要な結合テスト、dev反映後にスモーク・主要E2E、必要な追加検証を本番前に実施 |
| 復旧 | 互換性を確認してアプリ前版へ差戻し。戻せない場合は前方修正。DBは別途判断 |
| 緊急修正 | 短命ブランチ→PR→最低限のCI→本番承認を維持 |

GitHub Flowは運用方式の名称であり、GitHub ActionsやGitHubリポジトリを必須にする意味ではない。

## 3. 暫定案と保留事項

次は会話で提示した具体案を保存したもの。基本方針と区別し、実装前に最終確認する。

| 暫定項目 | 現在の案 |
|---|---|
| パイプラインの本数 | PR検証CI・main CI・CDの3本 |
| main保護 | 直接pushを禁止し、PR経由に統一 |
| PRの必須検証 | 自動のBuild validationをRequiredとして設定 |
| PR更新時 | 修正コミットの追加で自動再検証 |
| main更新時 | 既存PRの合格結果を即時失効し、最新mainとの組合せで再検証 |
| Work Item紐付け | PRにUser Story・Task・Bug等の作業項目を必須で関連付け |
| main CIの再検査 | 型・Lint・テスト・Trivy等を再実行し、配布対象のmainを検証 |
| SonarQube配置 | Community Buildはmain CIで解析し、Quality Gate合格をCD開始条件にする |
| App Serviceへの経路 | CDから対象App Serviceへ成果物を反映。mainから直接反映する別経路は併用しない |
| 承認待ち | 本番ステージのEnvironment承認チェックを利用し、待機中にAgent・並列ジョブ枠を占有しない |

明示的に保留した項目：

- PRの未解決コメントをマージ阻止条件にするか。
- Squash・Merge commit・Rebase等の許可するマージ方式。
- ポリシーを迂回できる主体と条件の詳細。

保留は、例外操作を自由に許可する決定ではない。必要な運用ルールは本番利用前に定める。

## 4. Boards・ブランチ・PR

- AgileのEpic／Feature／User Story／Taskを利用可能にする。全階層の作成を小規模開発へ強制しない。
- 作業ブランチからmainへPRを作成し、差分と検証結果を確認してマージする。
- 個人開発でもPRで変更記録・CI確認を残せるようにし、他者承認が必要な設定を標準必須にしない。
- mainへの直接push禁止とCI成功必須は、人の承認人数とは別に設定する。
- Azure ReposのPR検証はmainのBranch policiesにあるBuild validationで構成する。
- 検証対象はPRと対象ブランチの組合せ。作業ブランチの更新時だけでなくmain更新時の検証結果の失効も設定する。
- 既定案はmain更新で即時再検証。高頻度更新で待機が大きい場合は有効期限等を見直す。
- PR説明・担当者等だけの変更を理由に、コード検査を無条件で再実行する必要はない。
- 共通契約・依存関係・パイプライン定義の変更を検証対象から漏らさない。パスによる省略条件は実装時に検証する。

## 5. パイプライン構成案

| パイプライン | 起動 | 処理 | 成果物 |
|---|---|---|---|
| ① PR検証CI | PR作成・コード更新・必要な再検証時 | 型・Lint・テスト・Trivy・ビルド確認等 | 配布用として公開しない |
| ② main CI | mainマージ後 | mainの基本検査、SonarQube／Quality Gate、配布用ビルド | 版を特定して保存 |
| ③ CD | ②の成功後 | dev自動反映・検証→任意UAT→本番承認→本番反映・検証 | ②の保存済み成果物を利用 |

### PR検証CI

- 型チェック、Lint、単体テスト、ビルド確認、依存関係・シークレット等の検査を実施。
- 認可、Tenant分離、DB更新等の重要な結合テストを実施する。テストは隔離した非本番データを使用する。
- ビルド処理では一時ファイルを生成するが、配布用成果物として保存・昇格しない。
- SonarQube Community Buildの標準PR解析を前提にしない。SASTの配置は次節による。
- 本番の接続先・資格情報・変更権限をPRジョブに渡さない。

### main CI

- マージ後のコードと配布ビルドを検証するため、基本検査を再実行する暫定案。
- PR側と検査定義を共通化し、テスト・スキャンの設定差を抑える。
- 効率化はキャッシュや重複処理の整理で行い、別のコミットの合格結果を無条件に流用しない。
- フロント＋BFF、API、必要時DACPAC・移行SQLをビルド・梱包する。
- 成果物をコミットSHA・実行ID・構成要素の版に対応付けて保存する。変更がない構成要素は既存版の参照も管理する。
- 全必須検査の合格前にCDへ昇格しない。

### CD

- dev・任意UAT・本番をステージとして分ける。環境ごとにパイプラインを増やすことは必須にしない。
- 成功したmain CIの実行IDを指定し、その成果物を取得する。「最新」を毎回取り直して異なる版に切り替えない。
- devは自動反映。UAT利用時は受入対象の成果物を固定する。
- 本番は承認後、dev／必要な受入検証を通過した同じ成果物を反映する。
- フロントの接続先等は環境別の公開設定で切替可能に設計し、同じ成果物を使う方針と整合させる。秘密情報をフロントへ埋め込まない。
- 同一環境への反映が衝突しないよう実行を制御し、古い実行が新しい版を意図せず上書きしない条件を検証する。

3本はパイプライン定義の数であり、Agent数や購入する並列ジョブ枠の数ではない。共通YAMLテンプレートやスクリプトの数とも異なる。

## 6. 検査・テスト・停止条件

| タイミング | 基本内容 |
|---|---|
| PR | 型・Lint・単体テスト・ビルド、Trivy等の検査、重要な結合テスト |
| main | 配布対象の基本検査、SonarQube解析・Quality Gate、配布用ビルド |
| dev反映直後 | スモークテスト、主要操作のE2E |
| 本番前・重要変更時 | 必要な回帰テスト、DB移行検証、OWASP ZAP等の動的検査・k6等の負荷試験 |
| 本番反映直後 | データを壊さないスモークテスト |

- 全ての試験を毎PRで実行する構成にはしない。業務ルール・認可・データ分離など影響の大きい境界を重点確認。
- スモークテストは起動・主要API・必要な依存先接続等を確認。具体的な対象はアプリごとに定める。
- 本番スモークや負荷・動的検査で、実データ破壊や不要な外部通知を起こさない。
- 必須テスト・ビルド失敗、シークレット検出、重大なセキュリティ指摘は停止する基本方針。
- 重大度の対応表、既存指摘の扱い、誤検知の除外、スキャン不能・タイムアウト時の判断は実装前に定める。例外には理由・期限・承認記録を設ける。
- カバレッジの一律数値や全テストの具体製品を、本書で未承認のまま固定しない。

### SonarQube Community Build

- main解析は利用可能。標準の複数ブランチ・PR専用解析は利用可能と扱わない。
- main CIで解析し、解析送信の成功だけでなく当該解析のQuality Gateの判定まで確認する。
- sonar.qualitygate.wait=true等、利用Scanner・タスクに対応した方法で判定待ちと失敗伝播を実装・検証する。
- 不合格・解析失敗をCD成功条件に含めない。
- PR段階ではSonarQubeによるマージ前SASTがないことを明示する。必要なら別SASTまたは対応する商用版を検討する。
- Trivyの依存関係・設定・シークレット等の検査を、ソースコードのSASTと同等とは扱わない。
- 対応範囲は実際に導入するバージョンで確認する。

## 7. 任意のAIレビュー

- 既存の自作AIレビュアーを適用する。内部構築・モデル選定は本書の対象外。
- PRのレビュアー欄にAIレビュアーを追加すると実行する既存方式を利用。
- 初期開発や反復作業では省略でき、実行・完了をマージ必須条件にしない。
- AIの指摘は開発者が判断する。必須テスト・セキュリティ検査と別の補助機能として扱う。

## 8. Self-hosted Agent・接続・承認待ち

- SAST・Trivy・DAST等のOSSが配置された閉域環境を利用し、Self-hostedを基本にする。
- CI・非本番と、本番デプロイの実行環境・Agent Pool・実行主体・権限を分離する。
- 同じVMにAgentを追加し、Pool名だけ分けた構成を十分な分離とは扱わない。
- 本番Agentでは許可したデプロイ処理を実行し、PR由来の任意コードを実行させない。Pool・Service Connectionへの利用権限を限定する。
- 通常アプリ、CI、DB変更等の主体ごとに必要最小限の権限を設定。認証情報をソース・成果物・ログへ残さない。
- App ServiceのSCMデプロイ先、Private DNS、SQL、成果物保管先、Azure DevOps等への必要な到達性を確認する。
- OSS・Agent・OS・脆弱性データ等の更新方法と作業領域の残存データ対策を実装する。

本番承認はAzure DevOps EnvironmentのApprovals and checksで、本番ステージ開始前に待つ構成を暫定採用する。

| 状態 | パイプライン実行 | Agent・並列ジョブ枠 |
|---|---|---|
| devデプロイ・検証 | devステージ実行中 | 使用 |
| 本番承認待ち | 同じRunが未完了。本番ステージはWaiting | 占有しない |
| 承認後 | 同じRunの本番ステージへ進む | 空きを待って確保 |
| 本番完了 | 同じRunが完了 | 解放 |

承認で別Runを新規作成する方式ではない。並列ジョブ枠が1つでも、承認待ち中は別のPR検証・main CI等を実行できる。実際のジョブ実行中は枠を使うため他のジョブは順番待ちになり得る。Agent上で待機ループを実行して承認待ちを代替しない。

承認対象は成果物の版を特定する。待機期限、承認権限、個人開発時の承認可能者等は運用条件として設定する。他者によるPR承認を必須にしない方針と、本番手動承認は別のルール。

## 9. リリース・DB反映・復旧

- 1つのリリースでフロント＋BFF・API・DBの版と移行手順をまとめる。全要素を同時に原子的更新できる意味ではない。
- 変更のある構成要素だけを反映する。複数要素の変更時は前後互換性と部分失敗を考慮する。
- 通常例は互換DB変更→API→フロント＋BFF→スモーク。変更内容に応じて順序を定める。
- DB変更時だけ差分・移行SQL・必要な権限を反映する。旧カラム削除等は旧版が使われなくなった後のリリースへ分ける。
- 破壊的変更・データ移行等は差分と影響を確認し、必要な追加承認を設ける。
- スロット利用時はstageへ配置・確認後にスワップ。未利用時は通常デプロイ。DBはスワップで戻らない。
- 本番の通常変更は稼働中に行い、影響の大きい変更は事前告知した短時間停止を許容する。
- App Service Build Service等によるmain直結の独立した自動デプロイ経路を併用せず、検査・承認を通す経路に統一する暫定案。
- デプロイ・スモーク失敗時はリリース成功とせず後続処理を停止し、通知・復旧判断を行う。
- アプリ前版への差戻しは現在のDBとの互換性を確認して実施。古いDACPACの再適用を安全な復旧方法と扱わない。
- 差戻し不能なら前方修正、必要時はバックアップ復元とデータ損失・接続切替等の影響を判断する。
- 緊急修正もPR・最低限のCI・本番承認を維持。人の他者承認は一律必須にしない。本番直接修正を標準手順にしない。

## 10. 実装前チェックリスト・参考

詳細を別々の設計書に分割せず、以下を実装時に確認する。

- 暫定案と保留事項の最終確認。
- PRの必須CI、Work Item紐付け、main更新時の検証失効。
- YAML・共通テンプレートの検証と、パイプライン変更時の権限境界。
- Scanner・OSSの版、検査コマンド、停止条件、例外管理。
- テスト結果・スキャン結果の公開、保存期間・閲覧権限。
- 成果物の版固定、環境固有設定、古いRunによる上書き防止。
- 本番Agent・Pool・接続権限の分離とPrivate到達性。
- 承認待ちで別Runが実行可能なこと、拒否・期限切れ・再実行時の挙動。
- 旧新版共存、DB移行・部分失敗・差戻し・スモークの検証。
