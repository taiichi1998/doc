## 1. 目的・関連設計

## 2. 既決事項の継承

- Azure SQL Databaseを標準とし、アプリ別・環境別のDB分離を基本とする。UAT利用時は専用DBとする。
- 共通基盤モデルを再利用し、共通DBへの直接接続や全テーブルの配置を各アプリへ強制しない。
- テーブル名は単数形のlower_snake_case、カラム名もlower_snake_case。主キー名はid、参照カラム名は{参照対象}_id。
- Tenant固有Resourceはtenant_id必須、Projectは必要時のみ。共通マスター等に機械的にtenant_idを付けない。
- APIで認可し、Repositoryでも読取・作成・更新・削除・集計・バッチにスコープ制約を適用。RLSは要件に応じた追加防御。
- 業務処理・処理の組立てはService、DB操作はRepository。BFFやフロントから業務DBを直接操作しない。
- MI・最小権限・パラメーター化クエリ・接続プールを基本とする。
- バックアップ、復元確認、保持期間等はAzure構成・環境設計を参照し、本書で一律の数値を追加しない。

## 3. 決定事項

| 項目 | 方針 |
|---|---|
| 共通カラム | 更新する業務テーブルは作成・更新日時と作成者・更新者を標準化。関連テーブルや追記専用ログ等は用途に応じて省略 |
| 型 | 用途別の標準型を設け、長さ・桁数は項目別に定める |
| キー・制約 | 安定した内部IDと業務コードを区別。必須・一意・参照整合性はDBでも保証 |
| インデックス | スコープ・検索・結合・並び順に応じて設計し、実行計画で調整 |
| 同時更新 | 編集対象は楽観的同時実行制御を基本とし、競合を通知。黙って上書きしない |
| トランザクション | 一体で成功・失敗すべき更新をまとめ、短く保つ。外部API待ちを含めない |
| 接続管理 | プールを利用し、通常実行とスキーマ変更の権限を分離 |
| 削除 | 復元が必要なデータだけ論理削除、それ以外は物理削除 |
| スキーマ正本 | SQL Database ProjectをGit管理し、DACPACで差分反映 |
| データ移行 | 必要なデータ変換SQLを別途管理し、実行順序・履歴・再実行対策を用意 |
| 互換性 | 追加→移行→削除を基本とし、アプリ旧版との互換性を確保 |
| 本番停止 | 通常は稼働中に変更。影響が大きい変更は事前告知した短時間停止を許容 |

一般原則の具体化は作成者に一任された。ID生成方式、競合トークン等の具体製品・実装方式を、利用者が個別承認済みであるとは扱わない。

## 4. 共通カラムとデータ型

- 標準名はcreated_at、created_by、updated_at、updated_by。
- 作成者・更新者はクライアントの自己申告を信用せずAPI側で確定する。人間とバッチ等のシステム主体を区別し、システム処理を架空の人間に割り当てない。
- 初回作成時は更新日時・更新主体も作成時と同じ値にする基本実装とし、更新時に更新側の項目を変更する。
- この4項目は変更履歴全体を残す監査ログの代わりにしない。

| 用途 | 標準 |
|---|---|
| 文字列 | nvarchar(n)。長さを明示し、maxは必要時のみ |
| 操作・作成・更新日時 | datetime2(3)。UTCで保存し、APIでも時差の解釈を統一 |
| 日付のみ | date。業務日付を機械的にUTC変換しない |
| 整数 | int。範囲不足時はbigint |
| 金額・正確な小数 | decimal(p,s)。精度・小数桁・丸めを業務要件で設定 |
| 真偽値 | bit |
| NULL | 必須項目はNOT NULL。未設定に意味がある場合のみ許可 |

日時に元のオフセットや地域を保持する要件がある場合は別途設計する。bigint・decimalのNode.js/API境界での精度損失を防ぎ、必要な値は文字列等の契約で受け渡す。

## 5. キー・制約・インデックス

- IDの型・生成方法は共通実装で統一し、関連カラムの型も一致させる。具体方式は実装時確認事項とする。
- 業務コード、メールアドレス等の変更され得る値を、安定した内部IDの代わりにしない。
- 必須はNOT NULL、重複禁止はUNIQUE、同一DB内の参照整合性はFK、行内の値の条件はCHECK等で保証する。
- Tenant配下の関連には複合UNIQUE/FK等を用い、異なるTenantの親子を結べないようにする。認可は引き続きAPI/Repositoryで実施する。
- 別DBの参照はDB間FKを前提とせず、API等の契約と整合性確保手順を定める。
- 論理削除後の業務コード再利用可否に合わせて一意制約を設計する。
- 外部キー・検索対象だからという理由だけで全カラムにインデックスを追加しない。主要クエリの条件・選択性・更新負担を確認する。
- 主キーとクラスタ化インデックスを同一と決め付けず、選定したIDとアクセス特性に合わせて設計する。

## 6. 同時更新・トランザクション・接続

- 編集対象はバージョン値等を更新条件に含め、更新件数で競合を検出する。条件にはIDと必要なスコープも含める。
- 検出後は利用者へ再読込み・再確認を促し、古い入力の自動再送で上書きしない。HTTP応答はREST API共通仕様と整合させる。
- 業務上の不変条件は、楽観制御だけに依存せず制約・原子的更新・必要なロック等で保証する。
- Serviceが業務上のトランザクション境界を決め、Repository間で同じトランザクション接続を使用する。
- 分離レベルは対象DBの設定と不変条件を確認して選び、全処理を最高レベルに固定しない。
- 外部APIや通知とは単一DBトランザクションで原子的にならない。確実な連携が必要ならOutbox等を要件に応じて採用する。
- 接続を毎リクエスト無制限に作らない。取得・実行のタイムアウトとプール上限は環境別に設定する。
- リトライは一時障害を対象とし、回数を制限する。コミット結果不明や非冪等処理を無条件に再実行しない。
- スキーマ変更は通常APIとは別の実行主体・権限で実施し、アプリ起動時の自動変更を標準にしない。

## 7. 削除・監査

- 復元の必要性を各テーブルで判断する。論理削除対象のみdeleted_atや削除主体等を設ける。
- 論理削除対象は一覧・検索・集計等で既定除外し、復元・削除済み閲覧は明示的に認可する。
- 親子の削除・復元、関連の残存、コードの再利用を整合させる。無条件の連鎖削除を標準にしない。
- 論理削除は保存期限に基づく完全削除の代わりにならない。保持期間・完全削除・監査記録は案件別に定める。
- 監査は既存スコープ設計に従い、削除・復元等の重要操作を記録する。秘密情報は出力しない。

## 8. SQL Project・移行・デプロイ

- SQL Projectがスキーマの正本。DACPACとORM Migrationで同じスキーマを二重管理しない。
- DBアクセスはmssql等のドライバーを基本とする。ORMは任意とし、SQL Projectとの整合方法を検証する。
- CIでSQL Projectをビルドし、検証済みDACPACを環境間で昇格する。
- スキーマ・移行SQL・関連権限等に変更があるときだけDBデプロイを実施する。アプリのみの変更では不要。
- 対象DBに対する差分スクリプト・レポートを確認し、削除、型縮小、テーブル再構築、データ損失、長時間ロックを確認する。対象の状態が変わった場合は再確認する。
- データ損失防止設定を基本とし、検知を回避して無条件に反映する運用にしない。
- データ移行SQLには識別子・順序・チェックサム等による変更検知・実行履歴・再実行対策を設ける。スキーマ反映との前後関係を明示する。
- 大量変換は必要に応じて分割し、長時間トランザクションを避ける。途中失敗からの再開条件を定める。
- pre/post-deploymentスクリプトに一度限りの処理を無条件で記載しない。再デプロイでの動作を確認する。
- 互換カラム等を先に追加し、アプリ更新とデータ移行が完了した後に旧定義を削除する。
- 本番変更は承認後に実施。通常は稼働中に変更し、影響の大きい変更は事前告知した短時間停止を許容する。停止上限・時間帯は案件別。
- stage/prodの同時稼働とスワップを考慮する。スロットのスワップではDBは戻らない。
- 障害時は影響に応じて前方修正・互換性のあるアプリ差戻し・DB復元を選ぶ。古いDACPACの再適用を安全なロールバックとみなさない。
- 復元は復元時点以降の更新損失や接続切替も考慮し、既存の復旧設計に従う。

## 9. 実装時に確認する事項

設計書を細分化せず、以下をテンプレート実装・案件設定のチェックリストとする。

- IDの型・生成方式、監査主体の参照モデル、競合トークンとHTTP契約。
- 制約・越境関連防止・同時更新・削除復元の検証。
- 主要クエリの実行計画、プール・タイムアウト・分離レベル。
- 新規DB作成と既存DB更新、移行再実行、途中失敗、旧新版共存の検証。
- 本番の差分確認・承認・停止条件・復旧手順、移行実行主体の最小権限。
