## 実装・検証対象

### 1. End-to-Endデータフロー

以下が一連で動作することを確認する。

```text
Azure Cost Management / Azure APIs
        ↓
Storage
        ↓
Power BI Semantic Model
        ↓
Power BI 7ページ
```

確認対象：

- Cost Management Export：日次
- Power BI更新：日次
- Retail Pricesデータ：週次
- Advisor等の補助データ更新
- Activity Log取得
- Storage Lifecycle

### 2. データ突合

代表的な月・RG・Resourceを選び、Azure Cost Analysis等の元データと比較する。

最低限：

- 総コスト
- 月次コスト
- 日次コスト
- RG別
- Service別
- Resource別
- SKU別
- Tag別
- 予算
- Forecast

差異がある場合は、Cost Managementの列定義・通貨・償却・クレジット等の扱いを確認し、原因を記録する。

### 3. 計算ロジック検証

- 前月差額 / 前月比
- RG月額負担ルール
- 閾値までの残額
- タグ充足率
- 不正タグ判定
- 想定削減額 / 削減率
- 変更前7日平均 vs 変更後7日平均
- 変更前30日平均 vs 変更後30日平均
- 前日 / 前週 / 前月の増加額・増加率
- シミュレーションの月額差分 / 年額差分

境界値としてRG月額が閾値と同額、1円超過、1円未満のケースを確認する。

### 4. 7ページ確認

- 経営サマリー
- コスト分析
- 削減候補
- タグ品質
- コストシミュレーション
- 変更前後比較
- 予算超過原因分析

確認項目：

- 共通フィルター
- フィルターリセット
- ページ間のフィルター状態
- 最終更新日時
- 対象期間
- 金額単位
- ドリルダウン
- 全件表示方針
- 並び順
- 空データ時の表示

### 5. 更新失敗時

要件：

- データ更新失敗時も前回正常取得データを表示する
- 最終更新日時を必ず表示する
- 初期段階では専用通知・専用エラー画面を必須としない

テスト可能な範囲で更新失敗を再現し、既存の正常データが破壊されないことを確認する。

### 6. 冪等性・重複

- Cost Exportの再処理
- API取得処理の再実行
- 同一期間の再取得
- Power BI更新

上記でコストやRecommendationが二重計上されないことを確認する。

### 7. 性能・操作性

実データ量を想定して以下を確認する。

- ページ表示時間
- スライサー操作
- ドリルダウン
- Waterfall
- 全件一覧
- 直近12か月表示

不要な高カーディナリティ列、過剰な双方向リレーション、重いDAXがある場合は改善する。

### 8. セキュリティ・アクセス

初期要件：

- 部門内ユーザーは対象RG全体を閲覧可能
- 初期RLSは不要

不要なRLSを追加せず、Storageやデータ取得処理の権限は既存方針に従い最小権限とする。

### 9. ドキュメント更新

- `../TASKS.md` のPhase状態を更新する
- 各Phaseの実装結果・変更ファイル・設計判断を埋める
- 実際の構成と要件ドキュメントの差異を解消する
- セットアップ / デプロイ / 更新 / 障害時確認方法をREADME等へ記載する
- 将来機能と初期実装済み機能を明確に分離する
